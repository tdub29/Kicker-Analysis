# Superseded code, kept for the record

Nothing here runs in the current pipeline. It is the version that was replaced,
kept so the commit that replaced it can be read against what it replaced rather
than against a blank.

| file | why it was retired |
|---|---|
| `r/kicker_pipeline.R` | The 2023 original, and the source of the Python pipeline in the next row. Team grain, one wide home/away row per game, week 7 onward, 2005 to 2022: each team's kicking summed over the previous six weeks, field-goal attempts taken and allowed on fourth down, and a blend of the two called expected attempts (`homeexpatt`). Three things sit on top. `homeregressfp` applies hard-coded coefficients from the regression at line 717, which is fit on every row of the same table; refit on the shipped table they come back within 2%. `homehistoricalfantasy` averages the actual points of every row whose expected score and kick rate are within 5% of this one's, across the whole 2005 to 2022 table, so it includes the row's own result and seasons that had not happened yet. The "cash" model asks whether a kicker clears the 1.5 made field goals line (`homecash`, +1 or -1) and, for each team on the slate, reports a hit rate, units of profit and a p-value over every past row with similar expected attempts and kick rate. The hit rate is `(n/2 + profit) / n`, which doubles the distance from 50%: Buffalo's 68.2% under in `data/thisweekskickermodel.csv` is 51 of 88, 58.0%. The p-value is a Jarque-Bera test, which asks whether the +1/-1 outcomes are normally distributed, not whether the hit rate beats 50%. The thresholds quoted in its comments were found by searching that same history, and nothing is held out. It also runs `install.packages()` inside the script and cannot run top to bottom in a fresh session: `jarque.bera.test`, `ggplot` and `rsq` are called before their libraries load, and line 656 binds a `newdf2` that is never defined. |
| `feature_engineering.py`, `modeling.py`, `evaluation.py`, `pipeline.py`, `data_ingestion.py` | The original Python pipeline, a port of the R script: the same team-grain home/away table and the same formulas for expected attempts, `homecash` and `homeregressfp`, down to the hard-coded coefficients. Its modelling layer was 17 lines: a three-feature linear regression of `homefppg` on `adjhomeexpatt`, `homekick_pct` and `homexppg`, and nothing ever called it. It trained on home rows only, and `evaluate_predictions` was never called on a holdout, so no out-of-sample number existed anywhere. `homefppg` is the home kickers' points in that one game, not the season-to-date average it was once described as here; the evidence is in the data table below. |
| `config.py`, `utils.py`, `configs/base.yaml` | Configuration and utility helpers for that pipeline, moved out of `src/kicker_analysis/` and `configs/`. `config.py` loads `base.yaml` (seasons 2005 to 2022, weeks 7 to 20, a six-week window: the R script's settings) into a dataclass of `data/raw`, `interim`, `processed` and `outputs` paths. `utils.py` maps relocated teams back to each era's code (LAC to SD before 2016) and forward again. The current modules read no config file: each states its season floor as a named constant next to the reason for it, and `build_dataset.py` collapses every relocated franchise to its current code instead. |
| `features_v1.py` | Correctly lagged, and still not deployable. It fed the model observed temperature and wind, which rank 3rd and 7th by importance and do not exist before kickoff: of 255 unplayed games in the schedule file, 0 carry either, while rest, division game, surface and home field carry all 255. It also admitted the game-day roof state and two columns that correlate 0.992 with the season, which is a calendar clock wearing a feature's name. |
| `evaluate_v1.py` | Sorted a table by MAE and read a winner off the top. On this target that is nearly meaningless: predicting a constant 8.0 every week beat both gradient-boosted models. Its `top5_hit` metric was an artifact (constant predictions made it return the alphabetically first five player ids) and its feature-importance block ran on 34 rows. |

## Data

Both are objects the R script builds, `kickeranalysis` and `thisweekhist`. The
script itself writes neither: its only `write.csv` call is
`write.csv(newdf, "kicker")`.

| file | what it is |
|---|---|
| `data/kickeranalysisdf20052023.csv` | The R script's table: 3,206 games by 179 columns (plus R's row-name column), seasons 2005 to 2022, weeks 7 to 22. Beside the schedule's own columns, each is a team aggregate prefixed `home.`, `away.`, `actualhome.` or `actualaway.`, or a derived score named after a side (`homeexpatt`, `homecash`, `homeregressfp`). `homefppg` is that game's actual points: it is a whole number on every row, on all 3,154 rows that carry the game's own result it lies between PATs + 3 x FGs and PATs + 5 x FGs for that game, and it correlates 0.91 with that game's field goals made against 0.06 with the six weeks before. Replaced by `kicker_games.parquet`, which is per kicker rather than per team, starts in 1999, and is rebuilt by `build_dataset.py` rather than committed. |
| `data/thisweekskickermodel.csv` | The cash model's output for one slate, the eight teams of the 2022 divisional round (`currentweek <- 20`): the expected-attempts and kick-rate thresholds, how often that history recurs, over or under, observations, profit, hit rate and the Jarque-Bera p-value. Re-derived from the table above, the observation counts, profits and frequencies match on all eight rows, which is how the hit-rate error was found. |

The replacements are `build_dataset.py`, `features.py`, `model.py`, `backtest.py`
and `predict_week.py`. What each fix was worth, with numbers, is in `../METHOD.md`.
